# 新規 float32 HDR 可逆圧縮器 設計計画

## 1. 攻略目標

| 項目 | 現状チャンピオン | 我々の目標 |
|---|---|---|
| 圧縮率 (geomean) | `blosc_zstd9_bitshuf` **4.63x** | **5.5x 以上** |
| デコード | 893 MB/s | **400+ MB/s** (許容) |
| エンコード | 22 MB/s | **100+ MB/s** (改善) |
| 単一チャンネル float | (JPEG XL クラッシュ) | **対応** |

「圧縮率 +19 %、エンコード速度 +400 %」を同時に達成する。

## 2. なぜ Blosc bitshuf を超えられるのか

Blosc bitshuf の **未活用情報** を分析:

| 情報源 | Blosc が使えるか | 我々が使うか |
|---|---|---|
| ビット位置の相関 (BITSHUFFLE) | ✓ | ✓ (引き続き活用) |
| LZ77 マッチ (zstd) | ✓ | ✓ (引き続き活用) |
| **空間相関 (隣接ピクセル)** | ✗ | **✓ (新規)** |
| **チャンネル相関 (R≒G≒B)** | ✗ | **✓ (新規)** |
| **float の構造 (sign/exp/mantissa)** | △ (バイト粒度のみ) | **✓ (ビット粒度)** |
| **動的コンテキスト適応** | ✗ (固定辞書) | **✓ (rANS + コンテキスト)** |

Blosc は **transform + entropy** の 2 段構成で、間に「予測」がない。我々は **transform → 予測 → transform → entropy** の 4 段にしてここを埋める。

## 3. アーキテクチャ案

```
            ┌─────────────────────────────────────────────┐
            │  入力: float32 RGBA, W×H×C                  │
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
   [段階1] │  チャンネル可逆色変換 (R, G-R, B-R, A)      │  ← Blosc に無い
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
   [段階2] │  2D 空間予測 (LOCO-I/MED 式 float 版)       │  ← Blosc に無い
            │  各ピクセルを N/W/NW 近傍から予測           │
            │  → 残差 = pixel - predicted                 │
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
   [段階3] │  float→int 構造化変換                       │
            │  residual を sign/exp_diff/mantissa_xor へ │
            │  ※ 整数化することで以降の処理が安定        │
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
   [段階4] │  BITSHUFFLE (Blosc から流用)                │  ← 残差に適用
            │  各 bit を 8x ストリームに再配置            │
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
   [段階5] │  rANS エントロピー符号                       │  ← Blosc は zstd
            │  per-stream の適応モデル (order-1 文脈)     │
            └──────────────────┬──────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────────┐
            │  出力: 圧縮バイト列                          │
            └─────────────────────────────────────────────┘
```

### 3.1 各段階の意図と期待効果

**段階1: 可逆色変換 (RCT / YCoCg-R)**
- HDR でも R, G, B は強く相関 → 差分にすれば残差の分散が 30-50 % 減
- 完全可逆 (整数 lifting で実装。JPEG2000/JPEG XL でも使用)
- アルファチャンネルはそのまま
- **期待ゲイン: +10-20 % ratio**

**段階2: 空間予測 (LOCO-I 式 MED predictor の float 拡張)**
- 各ピクセル `x` を近傍 `N, W, NW` から予測:
  ```
  if NW ≥ max(N, W):  pred = min(N, W)   # 左下から右上のエッジ
  elif NW ≤ min(N, W): pred = max(N, W)  # 右上から左下のエッジ
  else:                pred = N + W - NW # 平面領域
  ```
- float 版では `min/max/+-` を IEEE754 上で行う (順序は ulp 単位で意味を持つ)
- 残差 = `x - pred` (float 減算)
- **期待ゲイン: +30-60 % ratio** (これが最大の伸び代)

**段階3: float 残差の構造化整数化**
- float の引き算は denormal や精度問題を生む
- 代わりに **bit-XOR (`x ^ pred` の uint32 viewing)** を使う:
  - 多くのビットがゼロになる (差分が小さい場合、上位ビットが一致)
  - 真の bit-exact 可逆
- もしくは **ulp 差分 (整数として隣接ピクセル番号の差)**
- **どちらが良いかは実装比較で決定**

**段階4: BITSHUFFLE (Blosc 流用 or 自前 NEON 実装)**
- 32 bit を 32 個のストリームに再配置
- 残差の上位ビットはほぼゼロ → 連続ゼロが LZ77 で激減
- libbitshuffle は arm64 NEON SIMD 実装あり (60+ GB/s)
- **期待ゲイン: +20-30 % ratio**

**段階5: rANS エントロピー符号 + per-stream order-1 文脈**
- zstd は汎用 → ストリームごとの統計に最適化されていない
- 32 個の bit-plane それぞれに **独立した適応モデル**:
  - sign plane: ほぼ 0 (RLE 強い)
  - exp planes: 局所的にクラスタ (order-1 文脈で十分)
  - mantissa planes: ほぼランダム (静的モデルで OK)
- ryg_rans (https://github.com/rygorous/ryg_rans) を参考実装に
- **期待ゲイン: +10-20 % ratio over zstd**

### 3.2 期待される総合性能

```
ベースライン (blosc_zstd9_bitshuf):       4.63x
+ 段階1 (色変換):           ×1.15 →     5.32x
+ 段階2 (予測):             ×1.40 →     7.45x   ← 最大の伸び代
+ 段階3 (構造化整数化):     ×1.05 →     7.82x
+ 段階4 (BITSHUFFLE 再配置): ×1.10 →    8.60x
+ 段階5 (適応 rANS):        ×1.10 →    9.46x
- 各段階の干渉 (現実的補正):  ×0.7  →    6.6x   ← 現実的目標
```

**現実的最終目標: 5.5-7x ratio (PIZ 2.93x の約 2 倍、Blosc 4.63x の 1.2-1.5 倍)**

## 4. 段階的実装計画

### Phase 0: 基盤整備 (3-5 日)
**目標**: 開発スケルトンと評価ループを整える

- [ ] Swift Package + Python ベンチ統合のセットアップ
- [ ] 「passthrough」コーデック (何もしない、ただ raw を出力) を 1 つ実装
- [ ] 既存ベンチに `our_codec_vN` として組み込めるアダプタ
- [ ] 段階別に enable/disable できる構造 (各段階を ablation 可能に)

**Go/No-Go**: ベンチに乗せて raw が 1.0x ratio で通れば OK

### Phase 1: rANS エントロピー符号の実装 (5-7 日)
**目標**: zstd の代わりになる rANS を実装し、生 raw + 静的モデルで動作確認

- [ ] ryg_rans 移植 (256-symbol, table-based)
- [ ] 静的頻度モデルでの圧縮・展開
- [ ] order-1 文脈モデル (前バイトを文脈に)
- [ ] **検証**: 生バイト圧縮で zstd_3 と同程度の ratio が出ることを確認

**Go/No-Go**: ratio が zstd_3 (2.84x) ± 20 % 以内なら OK。大きく負けるなら rANS 実装にバグ。

### Phase 2: BITSHUFFLE + rANS (3-5 日)
**目標**: Blosc bitshuf の自前再現で 4.0x 以上

- [ ] libbitshuffle の C コード移植 (NEON 含む)
- [ ] BITSHUFFLE → rANS のパイプライン
- [ ] **検証**: blosc_zstd9_bitshuf (4.63x) の 80 % 以上 ≒ 3.7x 以上

**Go/No-Go**: 3.7x 未達なら rANS チューニング不足。逆に 4.0x 超えたら順調。

### Phase 3: 可逆色変換 (2-3 日)
**目標**: 段階1 のゲイン (+10-20 %) を実証

- [ ] R, G-R, B-R 変換 (最簡)
- [ ] YCoCg-R 変換 (JPEG XL でも使用、より強力)
- [ ] **検証**: Phase 2 + 色変換で 4.5x 以上

### Phase 4: 空間予測 (7-10 日) ★ 山場
**目標**: float 空間で動く MED predictor を完成

- [ ] MED predictor の整数版 (デバッグしやすい)
- [ ] float 版 (IEEE754 ulp 演算で正しく動くか検証)
- [ ] XOR-based vs subtract-based 残差表現の比較
- [ ] エッジケース (denormal, +0/-0, NaN, Inf) の取り扱い
- [ ] **検証**: 全段階合わせて 5.5x 以上 (Blosc 超え)

**Go/No-Go**: ここを超えられないと意義なし。5.5x 達成が必達。

### Phase 5: 適応文脈モデル (5-7 日)
**目標**: 各 bit plane に最適な文脈モデルで +10-20 %

- [ ] sign plane: RLE + rANS
- [ ] exp planes: order-1 + 静的事前確率
- [ ] mantissa planes: 静的モデル
- [ ] **検証**: 6.5x 以上

### Phase 6: SIMD/並列最適化 (5-10 日)
**目標**: 100 MB/s エンコードを実現

- [ ] BITSHUFFLE の NEON 実装確認
- [ ] 予測器の SIMD 化 (4 ピクセル同時処理)
- [ ] チャンク並列 (256x256 ブロック単位)
- [ ] rANS の interleaved 実装 (32-way parallel)
- [ ] **検証**: 100 MB/s 以上、ratio は維持

## 5. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| float 予測が IEEE754 の罠で破綻 | Phase 4 が頓挫 | 早期に小型テストで ulp 演算を検証 |
| 段階の干渉でゲインが乗算しない | 目標 5.5x 未達 | ablation で寄与度を可視化、悪化要因を除外 |
| BITSHUFFLE の場所が悪い (残差後 vs 残差前) | 圧縮率劣化 | A/B 比較して最適配置を決定 |
| エンコード並列化が予測の逐次性で頭打ち | 速度目標未達 | 「区画並列、区画内逐次」で割り切る |
| XOR 残差が float 引き算より悪い | 段階3 のゲイン無し | 両方実装して選択 |

## 7. 実装言語の選択

| 段階 | 推奨言語 | 理由 |
|---|---|---|
| プロトタイプ (Phase 1-5) | **Rust** または C | rANS 系は既存実装 (ryg_rans, FiniteStateEntropy) が C ベース。Rust だと将来 Swift Package 化容易 |
| 最終統合 | **Swift + C** | Swift Package で配布、ホットパスは C ABI で呼び出す |
| 比較ベンチ | Python (現状維持) | 既存のベンチに乗せる |

代替: 全部 **Swift** で書く案もある (Apple 連携が強い、ARM 最適化済み)。性能チューニングは C/Rust より時間がかかるが、最終形は綺麗。

## 9. 早期に出来る "Quick Win" (Phase 4 と並行可能)

Phase 0-3 と並行で:

**Quick Win A: Blosc API への薄い前処理ラッパー**
- 色変換だけ自前で実装 → 出力を blosc に渡す
- 30 行程度の Python で書ける
- **見込み: 4.63x → 5.0-5.3x** (Blosc を超える最小工数)
- これだけで「Blosc 越え」の事実は作れる

**Quick Win B: HALF (16bit float) ベンチ追加**
- 同じ手法を float16 (EXR の HALF 型) でも測定
- HDR でもパイプライン途中は HALF が多い → 実用性高い
- 工数: 1-2 日
